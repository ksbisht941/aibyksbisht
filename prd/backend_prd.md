# Chatbot Backend PRD

This document outlines the API specifications required from the Python backend team to power the portfolio's AI chatbot widget.

## Overview
The frontend (Next.js) currently implements a floating chat widget with a simulated streaming API. To fully integrate the AI, the Python backend needs to expose a REST endpoint that accepts conversation history and returns a **Server-Sent Events (SSE)** stream of text chunks.

## API Requirements

### 1. Chat Completion Endpoint

**Endpoint:** `POST /api/v1/chat`

**Description:**
Takes a list of conversation messages and returns a streamed AI response.

**Request Body (JSON):**
```json
{
  "messages": [
    {
      "role": "assistant",
      "content": "Hello there! 👋 I'm Kuldeep's personal AI agent. Ask me about his MLOps experience, projects, or technical skills."
    },
    {
      "role": "user",
      "content": "What is his experience in MLOps?"
    }
  ]
}
```

**Fields:**
- `messages` (Array of Objects): The full conversation history required for the LLM context.
  - `role` (String): Either `"user"` or `"assistant"`.
  - `content` (String): The text content of the message.

### 2. Response Format (Streaming)

**Content-Type:** `text/event-stream` or raw chunked text stream (`text/plain` chunked).

The frontend relies on the Web Streams API (`ReadableStream`). To integrate seamlessly with the existing UI code, the backend should stream text chunks as soon as they are generated by the LLM (e.g. using `StreamingResponse` in FastAPI or similar).

## System Context (Prompting)
The Python backend will be responsible for injecting the **System Prompt**. The frontend will only send the user and assistant turns. 
The system prompt should instruct the LLM on its identity:
- **Identity:** You are an AI assistant for Kuldeep Singh Bisht.
- **Knowledge:** Kuldeep is an AI/ML Engineer specializing in PyTorch, MLOps, Next.js, and cloud systems.
- **Tone:** Professional, concise, and helpful.

## Error Handling
If the LLM fails to generate a response or times out, return an appropriate HTTP status code (e.g., `500 Internal Server Error`). The frontend will handle non-200 responses and display a generic fallback message to the user.
